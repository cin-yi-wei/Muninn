### 結論
Muninn 在 Discord 的基本收發（Gateway 收訊、切段、429 重試、按鈕、編輯訊息）已經夠用，但還不能完全取代舊系統：附件的收和送兩個方向都沒有，這是日常會碰到的缺口。
最該補的三項：
1. **收附件**：解析 `attachments`，只有附件沒有文字的訊息不能丟掉，並把 URL 或下載內容交給 claude。
2. **送檔案**：用 multipart 上傳本地檔案，並把 8MB 上限一起帶過來。
3. **Gateway RESUME**，加上 **```圍欄切段**與**網路瞬斷重試**，這三項依序補。
DM 支援、編輯訊息、引用回覆、`allowed_mentions` 是 Muninn 比舊系統多的部分。reaction、thread、MESSAGE_UPDATE、@mention 解析兩邊都沒有。

### 結論
Muninn 的權限閘門在核心流程上已經可以取代舊系統。按鈕與文字回覆、記住、逾時、auto_approve、多請求排隊都有對應實作，記住鍵的粒度還比舊版細。Muninn 少了「哪些操作值得問」的判斷層，目前完全依賴 claude 自己的規則，換過去之後會問的東西可能與舊版不同。
最該補的三項：
1. 危險指令判斷與放行區：在 `RequestPermission` 對 Bash 做低風險自動放行，或維持「問」的範圍與舊版一致。
2. scratchpad 與專案 memory 目錄的寫入自動放行，否則每份草稿或記憶都要按一次。
3. 在頻道或 admin 指令裡切換 auto_approve，不用改檔重啟。

以上第 1 點的判斷依據是我只讀了 Muninn 程式碼，沒有跑 claude 實測，所以「claude 預設會不會問一般 Bash」我沒有驗證。

### 結論
- **日常排程能取代舊系統。** cron、時區、catch_up、去重和崩潰一致性都有，去重的做法比舊系統嚴謹。
- **差在管理面。** 舊系統有 CLI（add、list、remove、test）、Web UI 和 admin API，Muninn 只有頻道裡的 MCP 工具、`!schedules` 和唯讀的 `muninn schedules`。這符合 Muninn「由頻道裡的 claude 管理」的設計，但人沒辦法繞過 claude 直接操作。
- **最該補的 1～3 項：**
  1. 補一個直接操作的 CLI 或小型 HTTP 入口，包括 add、remove、pause、run-now，讓人不靠 claude 也能管，對 claude 無回應時特別有用。
  2. 能替「別的頻道」的任務做管理（跨 binding），目前只能到該頻道去說。
  3. 決定遷移方式：要嘛寫一次性匯入工具，要嘛接受手動重建，並先修正 DESIGN.md:111 與 :119 的矛盾。

### 結論
目前 Muninn 在這個範圍**還不能取代**舊系統。它只剩「設定檔驅動」：新增、移除、暫停、恢復 binding 都要手改 muninn.json 再重啟整個程序，沒有聊天裡的管理指令，也沒有管理 CLI，也不會自動建或刪 Discord 頻道。能直接沿用的只有 worktree 建立（比舊的嚴謹）、單頻道的 `!status`、`!cancel`、`!restart`，以及 `paused`／`auto_approve` 欄位本身。
最該補的三項：
1. **設定熱載入加上 `/pause`、`/resume`、`/auto-approve`**：這三個只改旗標，改動最小，還能避免為了暫停一個頻道而重啟全部。
2. **`/bind` 與 `/unbind`（含 Discord 建頻道／刪頻道、wip commit、移除 worktree、失敗回滾）**：這是日常新增與收掉專案的入口，補了才算有管理能力。需要在 `discord/rest.go` 加建頻道與刪頻道，並在 `worktree` 套件加移除與 wip commit。
3. **管理 CLI 或控制頻道其中一個**：`muninn bind／unbind／pause／resume／list`。舊系統的「控制頻道 AI 助理」本質是讓人用自然語言呼叫這些 CLI，所以先有 CLI，再決定要不要保留控制頻道。

### 結論
Muninn 在這個範圍已經涵蓋日常最常用的部分：閒置回收、記憶體上限、`!cancel`／`!restart`、崩潰回放上限，以及權限逾時當拒絕。單看這些，可以取代舊系統的核心自保。要完全取代，還缺「不崩潰但卡住」與「登入過期」兩類故障的偵測。最該補的三項如下：
1. **無事件停滯 watchdog 加單輪逾時**：N 分鐘沒有 stream-json 事件就殺掉並 `--resume`，連續失敗就丟棄該 job 並通知頻道。
2. **auth 失效偵測與通知**：偵測 claude 回傳的 401 或 not logged in，通知頻道要人工 `claude /login`，並暫停重試。
3. **跨程序單例鎖（`state_dir` 的 flock）加實質的 `doctor`**：避免兩個 muninn 或舊 claude_cron 同時寫同一個 session，並檢查 claude 版本、登入狀態與 token。

每列的「已有」都附了 Muninn 的檔案與行號，不是猜的，但沒有跑測試或實際執行。

最該補的項目:
1. **圖片附件(photo / image document):** 補上 getFile、下載到本機,再把路徑交給 claude。同時讓純圖片訊息不被 telegram.go:325 丟棄。

### 結論
Muninn 目前完全沒有 Agent-to-agent 能力，這個範圍無法取代舊系統。Muninn 只具備通用的頻道 session、權限按鈕、worktree 建立與排程，沒有委派入口、角色、沙盒政策、任務狀態機和完成通知。
最該補的三項：
1. 委派入口加任務狀態機：用 unix socket 或 MCP tool 讓頻道 worker 派工，包含 `--resume` 追問、並行上限、查詢與取消。
2. 角色與授權等級（readonly／develop／full）：用 `--append-system-prompt` 加工具白名單，每個任務一個 worktree 沙盒，並加上無人值守的權限閘。
3. 完成通知回來源頻道：任務結束時直接把結果寫進 binding 的 inbox，worker 才會被喚醒。
caller 認證、webhook callback、Docker、Agent Card 都屬低優先，單機自用可延後。

### 結論
這個範圍的核心流程（入佇列、去重、依序處理、崩潰回放、重試上限、喊停、回覆切段、活動旁白）Muninn 都有對應實作，有些做得更好，例如活動旁白改成編輯同一則訊息。目前還不能完全取代舊系統，主要缺三項。tmux 專屬的機制都已正確排除。
最該補的依序是：
1. **附件下載給 claude 看**（圖片為先，再來是 Discord 長文字轉成的 .txt）。`chat.Message` 目前沒有附件欄位，這是日常最容易碰到的缺口。
2. **單輪逾時與卡死偵測**。加上之後，claude 掛住時 worker 不會一直卡住，後面的訊息也不會全部排隊。
3. **notify 通道，加上出站附件**（claude 或外部腳本主動發訊息、送檔案）。另外建議順手處理 sender 遇到永久性錯誤時會擋住整個 outbox 的問題。

### 結論
在這個範圍內，Muninn 已經能取代舊系統的日常運作：設定驗證比舊系統更嚴，開機啟動、優雅關機和 Discord／Telegram 多平台都有，systemd unit 也附在 repo 裡。缺的幾項（init、version、Makefile、release 打包、mock 平台、`.env`）都是便利功能，不影響每天使用。
最值得補的三項：
1. **設定熱重載或不重啟的 binding 增減**：新增或暫停頻道現在要重啟整個程序。
2. **`check` 補環境檢查**：確認 token 環境變數有設定、`claude` 與 `git` 在 PATH 上，讓 `check` 同時扮演 `doctor`。
3. **`version` 子指令加 ldflags 注入**：用 systemd 長期跑時，才能確認線上是哪一版。
